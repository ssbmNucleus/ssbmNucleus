# Custom Content: Characters, Stages, ISO Scanning

Three related systems for getting wholly new content into the vault and into
builds. Endpoint lists: [API_REFERENCE.md](API_REFERENCE.md).

---

## Custom Characters (`backend/vault/routes/custom_characters/`; install: `backend/projects/routes/custom_characters.py`)

Entirely new fighters added via m-ex (not costume swaps). Sources:

- **MexManager-exported ZIP packages**, through the unified import
  (`POST /api/mex/import/file`)
- **Scanning a modded ISO** (`POST /api/mex/scan-iso/mex-content` with
  `characters: true`) — extracts non-vanilla fighters out of an existing m-ex
  build; the same call can take its stages too

Vault layout:

```
storage/custom_characters/<slug>/
    fighter.zip     # original ZIP preserved for re-export
    fighter.json    # extracted metadata
    css_icon.png    # CSS icon for grid display
    csp_0.png ...   # per-costume CSP portraits
```

Tracked in `storage/metadata.json` under `custom_characters`. Operations:
list, detail, rename, delete, export (download original ZIP), serve
icon/CSP/stock images, and install into / remove from the open MEX project
(via MexCLI). Installed characters can be smoke-tested in-game via
`POST /api/mex/test-in-game/custom-character`; a specific custom-character skin
or bundled costume slot can be tested with
`POST /api/mex/test-in-game/custom-character-skin` (see
[INGAME_TESTING.md](INGAME_TESTING.md)).

### Standalone Classic demo archives

Custom-character scanning preserves source `<demoIntro>.dat` and
`<demoEnding>.dat` archives alongside code-referenced loose DATs. The m-ex
runtime loads these optional archives before falling back to `IrAls.dat` and
`GmRegEnd.dat`; custom roots such as ACE Wolf's may not exist in the fallbacks.
The pinned native `export-fighter` does not package these standalone files.

`vault/importing/custom_character_scan.py` adds only existing source files with
safe symbol names resolved inside the project's `files/` directory. The shared
scan/rescan path fills missing vault ZIP entries and preserves existing entries
case-insensitively. It leaves embedded standard demos alone and does not invent
missing animation data. MexCLI's existing loose-DAT installation path copies
these archives into the target project. A vault rescan does not retrofit
already-installed project copies.

Regression coverage is in `test_ace_build_scan.py` and the optional native
`test_custom_character_mode_roundtrip.py`.

### Steve v1.20 and ACE 2.0 Zero preservation controls

The 2026-10-15 source/package/build investigation (kept in the
`archive/pre-open-source-2026-11` tag) recorded verified release inputs, opt-in
native tests and actual grounded/aerial jump and up-special comparisons. Both reported symptoms remain unreproduced on
that baseline; no importer repair or report closure is claimed. The two native
tests require local, verified assets via the environment variables documented in
that record. Passing preservation tests alone does not establish gameplay.

### Built-in Giga Bowser setup and icon requests

First-run setup stages Giga's native inputs; the built-in setup action creates
four costume packages, portraits, stock icons, team-color indices and vault
metadata. The shipped CSS icon is copied both to `css_icon.png` and `icon.png`
inside `fighter.zip`. Frozen builds resolve this asset from the PyInstaller
bundle rather than the writable user-data root. Repeat setup checks the completed
fighter before requiring a seed directory, which successful builds remove.

Detail-header images must pass their URL through `backendMediaUrl()`. The icon
route is authenticated even when the PNG exists: a bare `<img>` URL receives 401.
`customCharacterIcon.test.js` evaluates the header's actual URL expression, so an
intermediate URL variable cannot bypass this regression check.

`test_first_run_builtin_staging.py` exercises source and packaged directory
layouts, real ZIP/metadata writes and PNG decoding, four costumes, repeat setup,
and the production-auth icon route. Native export, recoloring and rendering are
mocked; these tests do not establish real ISO extraction, native render quality,
or installed-app first-run correctness. Those require packaged acceptance tests.

### Any Climbers pairs (`backend/vault/climbers/`)

A pair is a vault recipe (`climbers: {leader, partner}`) that `pairs.materialize`
turns into an ordinary fighter package at install time: the leader is
duplicated into a new slot (`MexFighter.Duplicate`, sharing the donor's data
files) with `subCharacter` = the partner and `subCharacterBehavior` = 0
(spawn together). Two things make it play like the Ice Climbers:

- **The engine Gecko code** (`backend/data/any_climbers.ini`, generated by
  `vault/climbers/engine/gen_engine_code.py`, needs devkitPPC only at dev time).
  It gives any second entity Nana's follow AI, sets `has_follower` on the
  leader, swaps leader/follower on D-pad down (refused while either half is
  dead, asleep or respawning), and swaps `StaticPlayer.transformed[0..1]`
  with the control roles. `Player_GetEntity` uses that mapping to charge stocks;
  `Player_GetEntityAtIndex` uses it for follower lookup and respawn. Its indices
  are logical roles, not physical entity slots. The former `0x800BFE30` death
  hook is removed because the native logical follower lookup now resolves
  correctly. Without the mapping update, the controlled secondary fighter's
  death was free and its follower lingered on the respawn platform.
- **The kind alias block**, emitted per project by `engine_code.desired_source`
  and appended to that code at export. The clone leader has a new internal
  kind, and Melee's character code checks `fp->kind == FTKIND_X` before it
  lets kind-specific moves happen (Link's zair, Kirby's copy, Falcon's flame,
  Fox/Falco, Marth/Roy, Pikachu/Pichu ...). A C2 hook in `Fighter_procUpdate`
  rewrites the leader's `fp->kind` to its donor's after spawn, stashing the
  real kind in `ft_var51` (0x22F4) for the two consumers that need it: a Kirby
  copying the clone, and `Player_80036394`, whose exit hook answers the HUD
  stock and the results screen with the clone, so a Double Pichu shows the
  fighter you control instead of yellow Pichu. Donors are inferred from
  `files.fighterDataSymbol`.

`engine_code.ensure_code` runs on every export of a project that contains a
pair, test builds included (`engine_code.ensure_for_export`). It adds the code
when missing and **replaces it when the project's copy is older than the
bundled one** (`mexcli add-code` skips an existing name, so projects made on an
older app used to keep that app's engine code forever).

A pair can go without the swap: `pairs.set_no_swap(project, name)` lists it in
`climbers.json` beside the `.mexproj`, and that pair's alias entry sets the
leader's swap cooldown past any match length at its first frame. D-pad down then
does nothing for it, while other pairs in the project still swap. Plusle & Minun
are set this way by the Pokémon cast build; there is no UI for it.

A partner may itself be built as a pair: the game reads the sub-fighter from
the picked fighter alone, so the partner's own sub-fighter never spawns. What a
partner can't be is Ice Climbers, Zelda or Sheik, or a fighter that transforms.

`subCharacter` is an internal id. Before the m-ex fork's v2026.11.03, MexCLI's
`add-fighter` and `remove-fighter` compared it with the external id, so a pair
whose partner was the roster's last fighter moved onto the fighter just added;
the fork now compares internal ids, and `remove-costume(s)` moves the
red/blue/green team costumes with the costumes they name. Since v2026.11.09.1,
`reorder-costume` (swap) and `reorder-costumes` (splice) move them too, Nana's
with Popo's. The fork's `MexCLI.Tests` cover all of this without an ISO.

In-game verification was a one-off probe (`climbers_bug_probe.py`, removed in November 2026).
Its `swapped_respawn` scenario requires `--stock --bag <idle-human-ckind>`;
`--swaps 0`, `1`, and `2` exercise the original leader, the switched leader,
and switching back. It checks repeated KO stock loss, both fighters leaving the
platform, a free follower-only death, refusing a swap to that dead follower,
and restoring the pair after the remaining leader dies. Solo stock matches
end immediately and cannot validate this sequence.

## Custom Stages (`backend/vault/routes/custom_stages.py`; install: `backend/projects/routes/custom_stages.py`)

Entirely new stages added via m-ex's stage system — distinct from DAS stage
skins, which are alternate textures for the 6 legal stages.

Sources mirror custom characters: MexManager-exported ZIPs (the unified
`/api/mex/import/file`), scanning an existing build
(`/api/mex/scan-iso/mex-content` with `stages: true`), classic `stage.yml`
packages (converted by `backend/vault/importing/stage_yml_converter.py`), and the
**"Add as new stage"** action on a vault stage skin.

Raw `GrXx.dat`/`.usd` mods for the NON-tournament versus stages (`GrGr`,
`GrCs`, `GrBb`, ...) are **not** custom stages on import: `stage_detector`
covers every code in `core/stages.py`, so they land in the vault as stage skins
(`storage/das/<folder>/<id>.zip`, metadata `stages.<folder>.variants`) exactly
like the six DAS stages' variants, and share the vault stage page, folders,
sort, rename, delete, export and duplicate detection. Project-side they are
**replace slots** (`backend/projects/routes/stage_slots.py`, the non-tournament rows
of Install > Stages): the skin's DAT is written over the vanilla root file(s)
(both `.dat`+`.usd` for dual-language stages) or vanilla is restored from
`vanilla_refs.ensure_vanilla_ref`; slot state is derived by hash, not stored.

`POST /api/mex/stages/<code>/slot/add-as-stage` is the bridge to THIS system:
it wraps the skin into a stage package via
`backend/vault/importing/vanilla_stage_import.py` (the vanilla stage's own DOL
code tables from `vanilla_stage_specs.py`, the vanilla SSS icon/banner copied
out of the user's own game (`menu_refs.stage_art_path`; left out when not yet
derived), and a `nucleusVanillaStage` sidecar) and
imports it as an ADDED custom stage (the vanilla slot stays untouched). Because
`MexStage.FromPackage` resets the sound bank and playlist on install, the vault
entry carries that `vanilla_stage` sidecar and the install flows re-apply it by
patching the project's stage json (`_apply_vanilla_stage_fixups`). Adding a stage
anywhere in the app is one row in `core/stages.py`.

Vault layout:

```
storage/custom_stages/<slug>/
    stage.zip       # original ZIP preserved for re-export
    icon.png        # SSS icon, extracted for fast serving
    banner.png      # banner image for detail view
    stage.json      # extracted metadata
```

Tracked in `storage/metadata.json` under `custom_stages`. Operations: list,
rename, delete, export, serve icon/banner, install into / remove from the
open project, list stages currently in the project (`/in-project`), reorder,
and vault folder management (create/rename/delete/toggle — same model as
costume folders). In-game smoke test:
`POST /api/mex/test-in-game/custom-stage`. DAS stage skins use
`POST /api/mex/test-in-game/stage-skin`; a single live preview capture uses
`POST /api/mex/test-in-game/capture-stage-screenshot`. Bulk previews are
rendered offline instead, through
`POST /api/mex/storage/stages/render-screenshots` (see
[STAGE_HSD_RENDER.md](STAGE_HSD_RENDER.md)).

## ISO Scanning (`backend/vault/routes/iso_scan.py` + `backend/vault/importing/iso_scanner.py`)

`IsoScanResults` presents all selected scan targets in one categorized result
view. Custom additions are already saved; costume candidates remain selectable
until import. Optional icon lookups use the existing custom-character,
custom-stage and DAS vault list endpoints. DAS import records retain their IDs
and stage codes so preview matching does not depend on display names. A skin
scan failure after custom imports preserves those additions in the result view.

Rips new **costume skins** out of a list of vanilla/modded ISOs as a
background job:

1. ISO extraction uses the built-in GameCube reader. The optional
   `GET /api/mex/iso-scan/preflight` reports native support.
2. `POST /api/mex/iso-scan/start` with `{ "iso_paths": [...] }` (`.iso`/`.gcm`;
   nkit not supported) — starts a scan thread and returns a `job_id`.
3. The pipeline (in `iso_scanner.py`) extracts each ISO, hashes character DAT
   files against the vault and vanilla hashes to find *new* skins, runs
   Slippi-safety validation, and generates a CSP preview per candidate into a
   per-job work directory. Progress is emitted over WebSocket as
   `iso_scan_progress` (`{ job_id, status, message, percent }`).
4. The UI polls `GET /api/mex/iso-scan/{job_id}` every 1.5 seconds, and also
   reads immediately after start, reconnect and completion events. Final
   candidates are grouped by character; unreadable ISOs appear in
   `extraction_failures` (all failed means an error). The UI renders thumbnails from
   `GET /api/mex/iso-scan/{job_id}/csp/{key}/csp`, and the user selects which
   to keep.
5. `POST /api/mex/iso-scan/{job_id}/import` imports the selected candidates
   into the vault; `cancel` / `DELETE` abort and clean up.

Note: extracting *m-ex custom content* (fighters and stages) from a build is
the one `POST /api/mex/scan-iso/mex-content` call in the custom characters
blueprint — the iso_scan blueprint is specifically for costume skins.


Stage variants imported through `/api/mex/das/scan-iso` also receive 768×432
previews from the HSD renderer. A warm CSP worker handles stage jobs without
Dolphin or an ISO rebuild. Rescans fill missing previews for previously imported
variants, preserve existing screenshots, and return duplicate entries under
`skipped` with their saved image URLs. Preview failure keeps the stage ZIP.
See [STAGE_HSD_RENDER.md](STAGE_HSD_RENDER.md) for camera profiles and limitations.
