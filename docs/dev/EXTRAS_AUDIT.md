# Extras Audit — verifying extra mods against in-game reality

The extras system (`backend/core/extra_types.py` + `vault/routes/extras/` (routes) + `vault/extras/` (engine) +
`frontend/src/shared/data/extraTypes.js` + the editors/previews under
`frontend/src/vault/extras/` and `.../projects/characters/`) is a set of DAT
patch recipes with UI previews. Many were authored from community offset lists
and have never been verified frame-by-frame in game. **This doc is the
workflow for auditing each one and fixing what doesn't match.** The goal per
extra: offsets hit the right bytes, the patch changes the intended effect, the
layer names/preview tell the user the truth, and both config mirrors agree.

## Community #110: Spooky Phantasm (2026-10-14, local review candidate)

**Reproduced and repaired in `bb32166a`, not released.** The
Discord report
does not specify the installed version, exact variant or import entry point.
The [published mod](https://ssbmnucleus.net/post/16178/spooky-phantasm) supplies
four Falco DAT variants. The baseline importer rejected the normal blue DAT
with `Could not read applicable sideb colors`; this was not a PNG import failure.

All four variants replace Falco's article-3 afterimage geometry and raise material
alpha from 0.3 to 0.8. The old color marker is absent, and a color recipe cannot
represent the skeleton mesh. Animelee and normal variants share the corresponding
blue/green afterimage graphs; their bundled blaster differences are unrelated.

`vault/extras/sideb_model.py` validates the bounded static, untextured,
single-joint/single-DObj/single-PObj graph before importing it. It validates
relocations, vertex arrays and display-list indices, stores a layout-independent
model signature, and transplants only that graph. Target fighter attributes,
states, animations, lasers and blaster remain intact. Both config mirrors flag
this capability on Falco side-B only. The UI identifies an afterimage model and
offers rename/delete instead of color controls that would describe the wrong shape.

Install and export use the same helper. Same-model installs are idempotent.
Selecting a color extra or restoring vanilla restores the original shape first.
Valid append rollback is exact; native save/reopen can relocate or discard the
undo record, so the fallback selectively transplants the original graph from a
vanilla reference. It preserves later edits and never truncates at stale offsets.
Color operations follow the active material, not obsolete markers left behind by
a native rebuild. Unsupported structures or missing required references fail
without publishing a partial file. General textured/rigged model support and
side-B PNG authoring are outside this change.

## The driver

`backend/devtools/extras_audit.py` (run from `backend/`, Slippi closed, no other
mexcli build running):

```
python devtools/extras_audit.py --char Marth --extra sword                 # full run
python devtools/extras_audit.py --char Marth --extra sword --skip-game     # static+build only
python devtools/extras_audit.py --char Marth --extra sword --iso <prev.iso># re-capture only
python devtools/extras_audit.py --char Marth --extra sword --vanilla       # unpatched control
python devtools/extras_audit.py --char Marth --extra sword --colors inner=00FF00,outer=FF00FF
```

Three stages:

1. **offsets** — diffs the config's claimed `vanilla` values against the real
   vanilla DAT bytes in `storage/test-base/files/` (no boot). `size`-format
   layers are byte-compared; matrix/multi-offset formats print raw bytes for
   eyeball review. NOTE: a pass here only proves the offsets point at the
   claimed bytes — **not** that the byte semantics are right (the sword case
   below passed this stage while being wrong).
2. **build** — copies `storage/test-base` (a full mex project), patches the
   target DAT with **maximally distinct test colors** (pure green/blue/magenta/
   orange... one per layer) using the app's own `apply_hex_patches`, exports an
   ISO via MexCLI (`output/extras-audit-<char>-<extra>.iso`).
3. **game** — frameshots the move(s) that show the effect (see
   `AUDIT_HINTS` in the driver: frameshot char + `move:frames` specs), with a
   flat gray background (`--plain-bg`, the Achilles no-stage-textures pokes) so
   colors read unambiguously. Captures + an `applied.json` (colors written,
   preview semantics) land in `app/scratch/ingame/extras-audit/<char>-<extra>/`.

Then compare: does each test color appear where the UI preview/layer name says
it should? If not, find the true semantics — **the melee decomp
(`projects/melee`) is ground truth** (find the struct + the render code) —
then fix BOTH config mirrors, the editor modal, and the preview, and re-run
stages 2–3 to confirm.

**When implementing a 🔴 from the reference: verify the marker bytes first.**
The reference's `CF_##`/`07_07_07` offset citations are often line starts, not
exact marker positions (off by 1–8 bytes). Dump the vanilla bytes and confirm
the `CF`/`07 07 07 04` marker before adding the layer — a patch at a shifted
offset can corrupt the effect script and **hang the game** (the Firefox `flare`
learned this). Multi-extra builds: hex patches are applied before texture
imports (HSDRawViewer re-saves the DAT and may shift the layout).

## Mission pipeline

Per-character work runs as subagent missions structured by
**`docs/dev/EXTRAS_MISSION_TEMPLATE.md`** (MAP on a strong model → WIRE on a
cheaper one → final capture eyeball in the main session). The template holds
the standing rules and the accumulated-lessons list — update it, not
individual prompts.

## Fast mapping: live RAM pokes (`shared/ingame/datram.py`)

The build→boot cycle (~5 min) is for FINAL verification only. For the
byte→visual **mapping** work ("which record drives which flame?") use
`shared/ingame/datram.py` (or the spec-driven `backend/devtools/effect_probe.py`): boot a
vanilla ISO ONCE, locate the loaded DAT image in MEM1 (`DatRam.locate()`
window vote — the real image scores high but not perfect because pointer
fields are relocated in place; data bytes are verbatim), then
`poke(file_offset, rgb)` → redo the move → capture. Seconds per experiment;
validated by turning the up-B trail fire green live (2026-07-01).

Gotchas that already bit:
- **Verify pokes at the true base by readback**; a low-vote candidate can be
  a false positive (`0x807xxxxx` u16-array lookalike), and a signature string
  can occur **more than once inside the file** — check self-occurrences
  before treating a hit as a second copy.
- **A dead live-poke ≠ dead offset.** Some data may be consumed when the
  effect system initializes at match load; if a region shows nothing live but
  a working community mod changes it, confirm with ONE build-path run before
  declaring it irrelevant.
- **Community-mod diffs contain shrapnel.** Recolor mods are often global
  color find-replace over the whole file, so their changed regions include
  same-colored bytes that do nothing (EfFxData `0x1A884/0x1AAA4/0x1AC84`
  tables poked live with no visible change on up-B). Treat diff regions as
  candidates to bisect, not answers.

## Case study: sword trails (fixed 2026-07-01)

The audit's first find, and the template for what a mismatch looks like:

- Config claimed 3× RGB (`main`/`secondary`/`tertiary`) at e.g. Marth
  `PlMs.dat 0x3948`. Stage 1 passed (bytes matched the claimed vanilla).
- Stage 3 with green/blue/magenta showed a solid **magenta** trail with a
  **reversed fade** (transparent at the blade). Decomp
  (`it/items/types.h itSword_UnkBytes` + `ft/ftafterimage.c`): the 9 bytes are
  `[alpha_blade][alpha_tail][inner RGB][pad][outer RGB]` — a two-color ribbon
  with an alpha fade, not three colors. "main" was two alpha bytes + one color
  channel; vanilla Marth is inner-cyan/outer-white (not red/yellow/white).
- Fix: `inner`/`outer` layers (+ `alpha_blade`/`alpha_tail` as non-UI BYTE
  layers) in both configs for Marth/Roy/Link/Young Link; SwordEditorModal +
  both SwordPreviews now draw the real ribbon (legacy saved mods map
  bug-compatibly). Re-verified in-game: green→magenta ribbon, correct fade.

## Offset safety: guard + relocation

Every offset in `extra_types.py` was marker-verified against a specific build
of a vanilla DAT. But a DAT can get **re-saved** by HSDRawViewer (texture
import, model import) between when a mod's offsets were captured and when
they're applied — and a re-save can shift every offset after the edit point.
A shifted write is silent corruption at best; per template lesson #1, a
shifted `070707`/CF write into a particle *script* can **hang the game**.

`backend/vault/extras/relocate.py` is the safety net wrapped around the
shared write paths (`apply_hex_patches`, `patch_shine_sparkle_color`) in
`color_patch.py`. It never changes behavior for a vanilla-shaped file; it only
activates when a write would otherwise land on the wrong bytes:

1. **Guard.** Before writing at offset `O`, read what's actually there. If it
   matches the expected vanilla bytes (from the config's `vanilla` dict) OR a
   previously-applied color the caller already trusts (`also_valid`), write
   exactly as before — this is the common case and costs one extra read.
2. **Relocate on guard failure.**
   - **ptcl-bank operands** (CF / RGB writes into an `Ef*Data.dat` that has a
     real particle bank): parse the VANILLA reference file
     (`storage/test-base/files/<target_file>`) with `shared/rendering/ptcl_parse.py`
     to identify the operand by **(script index, opcode kind, ordinal within
     script)** — an identity that survives a re-save because script content
     and order don't change, only absolute file offsets do. Parse the TARGET
     file the same way, look up the same identity, and verify the candidate
     operand is wide enough for the write before blessing it.
   - **Model-region blocks** (`070707`, and by extension `42_48`/`98`
     matrices, not yet wired into a live write path): signature-scan the
     target file for the marker bytes bracketed by enough vanilla context to
     be unique (shrinking the context window before giving up). Requires
     **exactly one** hit — ambiguous or zero hits both fail the relocation.
3. **Skip loudly, never write on a failed verify.** If relocation fails (no
   hit, ambiguous, or the final byte-verify at the candidate still doesn't
   match), the layer is skipped: a `logger.warning` names the extra id,
   layer, and both the original and any candidate offset, and the skip is
   recorded in `install_extra`'s `offsetSkips` response field (additive; a
   clean install that never triggers a guard failure does not see the key).
   The file is never touched for that layer.

Opt-in, not automatic: a write path only gets guarding if it's handed a
`safety` context via `helpers.make_write_safety(dat_path, extra_id,
target_file, vanilla_map)`. The `/install` route in `colors.py` builds one from
the extra type config's `vanilla` dict and threads it through; calling `apply_hex_patches` /
`patch_shine_sparkle_color` without `safety` (as any other caller still does)
is byte-for-byte the pre-existing behavior.

**Coverage:** the `98 00 ##` matrix branch of `apply_hex_patches` was already
guard-safe by construction (`patch_matrix_colors` only overwrites entries
matching the declared `vanilla` bytes within the given range, so a shift that
moves the WHOLE range out from under `start`/`end` is the only failure mode,
and that's a config problem the offset-safety layer doesn't fix — the matrix
itself must still be found first). `texture_recolor` extras have their own
live-measure/hue-detection logic (`texture_recolor.py`) that reads the actual
current dominant hue rather than trusting a stored offset, which is a
different (already shift-tolerant) strategy — left untouched. `laser_ring`'s
hue-track bytes and the `find_*_offsets` dynamic detectors
(`get_dynamic_offsets`) are unaffected; they already re-scan the file by
signature on every build and run upstream of this layer.

Tests: `tests/backend/test_extras_offset_relocation.py` (15 cases) — clean
vanilla write, re-applied write, a genuinely shifted `EfFxData.dat` fixture
(built by inserting bytes into the Models[] region of the REAL vanilla file
and fixing up the HSD archive header + effect-table pointers, so every ptcl
color operand moves by a constant offset — not a synthetic byte string),
ambiguous/failed relocation → skip with no write, and 070707 signature
relocation.

**Operand identity is the script-wide ordinal.** `_identify_ptcl_operand`
numbers an operand by its index in the script's FULL color list, so
`_find_ptcl_operand_by_identity` indexes that list and checks the kind. It
used to index a kind-filtered list with the same number, which picked a
different operand whenever PrimCol and EnvCol interleave (e.g. Fox's charge
flames in `EfCoData.dat`): a shifted install wrote into the wrong operands.

**Reads use the same resolution** (`helpers.resolve_current_colors`, behind
`GET /storage/extras/current`, the Install page's "Currently in MEX" card).
Each config-offset layer is located exactly as its write would be (guard,
neighborhood guard, ptcl identity, model signature, model-TEV owner proof;
shine channels via `locate_shine_color_slots`, the slot finder
`patch_shine_color_slots` writes through). Formats written in place without
relocation (98 matrices, `42_48`, direct `size` spans) are read only while
their neighborhood still matches the vanilla file. The neighborhood compare
masks every color span configured for that FILE (`file_color_mask_spans`),
so a recolored sibling effect never makes a layer look shifted. A layer
that can't be located is reported in `unknownLayers` instead of read from
the stale offset, and the verdict compares each layer with the vanilla
file's exact bytes at the same slot (not the config's representative
swatches -- 27 extras used to read "Custom" on an untouched project).
Dynamically detected layers are read where detection found them, as before.
Tests: `tests/backend/test_extras_current_read.py` (every color extra reads
Vanilla on the vanilla files; recolor/restore round trips; sibling recolors;
shifted and unrelated files; shine by vertex identity; units).

## User-report triage: "my extra doesn't look right in game"

Two one-liners settle any report like this (worked example: the 2026-07-03
Bowser blue-fire report, `breath_texture` row below):

1. **What is actually in the project file?**
   `python devtools/extras_doctor.py --project <name> --char <Char> [--extra id]`
   reads every configured layer from the project's target DAT and reports
   per-layer VANILLA / MODDED plus offset resolution (in-place / RELOCATED /
   UNRESOLVED = writes silently skipped). `--project` takes a name under
   `%LOCALAPPDATA%/SSBM Nucleus/projects` or a path. texture_recolor extras
   report their current dominant swatch vs vanilla.
2. **Route on the result:**
   - Layers VANILLA or UNRESOLVED → the INSTALL path failed (guard skips,
     wrong project open, mod saved without colors). Check the app log's
     `[relocate] SKIP` lines and the install response's `offsetSkips`.
   - All layers MODDED with the right colors but the game still shows wrong
     colors → a COVERAGE gap: some other asset draws the visible pixels
     (texture bank, item model, common-bank effect). Route to a MAP mission
     (`docs/dev/EXTRAS_MISSION_TEMPLATE.md`) — the Bowser case was the flame-body
     texture, found via the decomp (`itkoopaflame.c` spawns the ptcl effect
     once per flame item; sustained/landed fire = the item's textured quads).
3. **In-game ground truth for the fix:**
   `python devtools/extras_audit.py --char <Char> --extra <id>` builds a test ISO with
   the extra applied and captures the AUDIT_HINTS frames. Close any open
   Dolphin first (an already-running instance makes the harness's input pipe
   never appear). `--iso <path>` reuses the built ISO on re-runs.

## The master target list

**`docs/wiki/reference/color-effects-reference/Effect-Offsets-Reference.md`** (linked
from the app wiki, mirrored to the website) is the big list this campaign works
through: ~200 documented offset blocks across 18 characters plus the CSS/SSS/

(offset known, not exposed yet). The audit means: **verify every 🟢 with this
workflow, and implement 🔴 entries as new extras** (each new extra gets audited
the same way before it ships). Mark verified entries with ✅ in that doc.

**Hard-won texture-extra gotchas** (baked into `texture_targets` +
`vault/extras/textures.py get_texture_targets`):

1. **Enumerate exhaustively.** The first sweep stopped at 3 textures/model;
   EfCa `Models_0` actually lists **ten** (`Models_1` ten more). Probe indices
   until the CLI errors.
2. **TObjs share image nodes.** A model's flat texture list repeats one image
   at several indices (EfCa Models_0: 10 entries = 3 unique images; EfFx
   Models_4 idx 1+2 = 1 image). Importing at ONE index recolors every TObj
   sharing that node — and export→shift→import at a SECOND index of the same
   node shifts it AGAIN (a 180°+180° run came back vanilla and initially
   looked like "extra doesn't work"). Config rule: **one target per unique
   image node** (dedupe exported PNGs by md5 first).
3. **Decomp id mapping** (finds which Models_N an effect uses without boots):
   fighter code calls `efSync_Spawn(id)`; ids 0x479–0x4BA route through
   `ef/efalt.c`'s switch to `efLib_Create*(internal_id)`; internal_id/1000 =
   effect file, %1000 = data-table entry = `Models_N`. E.g. Firefox charge
   1163→0xBBB=entry 3, flight 1164→0xBBC=entry 4, Falcon Punch 1167→0xFA0+0xFA1
   = entries 0+1.
4. **Particle textures use a separate bank.** The model `--texture` CLI
   requires a JObj endpoint and does not walk `TextureGraphics`.
   `ptcl_texbank.py` and the raw `texture_recolor` path do address that bank.
   Trace model animation events and fighter subactions before assigning a
   particle script to a move: Fox flight uses EfFx group-3 palettes, while
   charge flames use EfCo scripts 299/300 RGB operands. See the correction above.
5. **Hue ≠ final pixel color.** The effect's vertex/material colors modulate
   the texture (Firefox cone at +180° reads green because warm vertex colors
   multiply the cyan texture; Falcon's bird reads true cyan). Judge shifts by
   "changed vs vanilla", not by predicted hue.
6. **The import never repacks the file (bug 11-19).** HSDRaw's `--texture
   import` re-serializes the whole archive, which moved the bytes the colour
   extras in the same DAT address by vanilla offset (a Falcon Punch fire hue
   made 9 of 10 flare-line writes and 13 restore groups fail). `_import_over`
   now runs the native import on a temporary copy and
   `vault/extras/texture_layout.py transplant_texture` copies only the
   texture's pixels and palette back in place. A shared buffer changes once for
   every TObj on it, as HSDRaw's own import does. A texture that would need
   another size, format, palette length or mipmaps is refused and the file is
   left alone. Projects repacked before the fix are not repaired.
